# Decisions

Choices the [blueprint](./BLUEPRINT.md) leaves open, one line each (Agent handoff, rule 4).
Changing an AD-xx is not done here: propose a new AD row in the blueprint and stop.
Hard-to-reverse choices beyond the blueprint get an [ADR](./adr/README.md).

| D-012 | 2026-10-12 | While a code is active a node accepts any client cert, for `/identity` and `/pair` only; a successful pair replaces the trusted controller. | D-013 | 2026-10-12 | LAN `GET /status` in M1 returns `agent_id, role, version, uptime_s, health, backups:[], problems:[]`; `store` arrives in M2. Local `/status` adds `agent_id`, `fp`. | Only what M1 can fill truthfully. |
| D-014 | 2026-10-12 | CLI `<agent>` = exact agent_id, else hostname (any case), else a unique agent_id prefix of at least 4 chars; ambiguity lists the candidates. | Nobody types a UUID; never guess between two PCs. |
| D-015 | 2026-10-12 | Discovery results are cached in controller memory; `pair` needs a `discover` or `agents add` in the same agent run. Discover refreshes hostname/address of a paired agent whose fp matches. | Pairing must pin the fp seen before the code is sent; DHCP changes heal on the next discover. |
| D-016 | 2026-10-12 | Role logic lives in package `coord` behind `localapi.Backend` (not in the blueprint's package list). | Keeps `localapi` free of LAN code and the role switch in one place. |
| D-017 | 2026-10-12 | Windows firewall rules `Sevjala-LAN-API` (TCP) and `Sevjala-Discovery` (UDP): port-scoped, inbound allow, all profiles; install recreates them, uninstall removes them. | Rule names without spaces survive `netsh` quoting; port scope survives moving the binary. |
| D-018 | 2026-10-13 | `sevjala code` shows the node's first 16 fingerprint hex chars; `pair` requires `--fp` and checks it against the discovered fingerprint before any network call (409 "do not pair", the code is not consumed). | Closes I-5: a LAN device answering discovery could capture the HMAC proof and brute-force the 6-digit code offline. 64 bits is out of reach for certificate grinding. |
| D-019 | 2026-10-13 | Detection (and M4 restore) uses the `mysql`/`mariadb` client binary next to the dumper; no Go MySQL driver. | Keeps the blueprint's dependency list; the client ships with every XAMPP. |
| D-020 | 2026-10-13 | The DB password lives in the OS keyring (service `sevjala`, account `db`), written by the agent (SYSTEM/root) through `db set`. Linux without a Secret Service uses AES-256-GCM `secrets/db.enc` keyed by `secrets/key` (0600) and logs `keyring_fallback`. Child processes get it only via `MYSQL_PWD`; an inherited `MYSQL_PWD` is dropped; client stderr is scrubbed of it. | Blueprint: secrets in the keyring. The CLI user's keyring is not the service's. `MYSQL_PWD` keeps it off argv and disk. |
| D-021 | 2026-10-13 | Dumps add `--default-character-set=utf8mb4` to the blueprint's flags. | The 10.4 client defaults to latin1 and mangles or rejects 4-byte characters (seen in the integration test). |
| D-022 | 2026-10-13 | New dependencies: `github.com/zalando/go-keyring` (blueprint-named) and `golang.org/x/term` (no-echo password prompt). | `x/term` is the standard no-echo prompt and depends only on `x/sys`; both build with go-win7. |
| D-023 | 2026-10-13 | Node store default `<data-dir>/store` (inherits the locked ACL); `min_free_bytes` default 2 GiB; a PUT that would cross it is refused upfront with 507. `config.Write` writes every key, so a fresh install shows all defaults. | Backups stay admin-only by default; a full disk fails fast instead of mid-write. |
| D-024 | 2026-10-13 | Until M3 policies, every backup goes to every paired node; `backup now` without `--tag` tags it `manual`. | Owner choice; a manual backup must not look like a scheduled tier. |
| D-025 | 2026-10-13 | A dump in progress or failed exists only in controller memory (`dumping`/`failed`); the `backups` row is written after the rename and manifest (blueprint step 4). A controller start deletes `staging/*.part`. | No half-made rows; a restart forgets only what the log already recorded. |
| D-026 | 2026-10-13 | Transfer retries after 30 s, 2 min, 10 min; then `failed`, or `offline` when no attempt connected, until M3. 400/403/409 and a TLS rejection are not retried. A restart requeues `pending` and `transferring` copies. | Blueprint backoff without M3's status cycle; a node re-paired elsewhere should not burn twelve minutes. |
| D-027 | 2026-10-13 | `PUT /backups/{id}` uses `Expect: 100-continue`; an identical stored copy answers 200 without reading the body. The node allows 60 s between body reads; the controller cancels after 60 s without progress. | A lost 200 then costs no re-transfer; a hung peer frees its slot (verified with a frozen node in the Docker run). |
| D-028 | 2026-10-13 | `backup_copies.last_error` survives retries until the copy is verified; the backup state is recomputed on every copy change (`created` while any copy is pending/transferring, then `distributed` or `partial`). | The operator sees why a copy is retrying. |
| D-029 | 2026-10-13 | A node scan reports every corrupt case (size mismatch, manifest without file, file without manifest, unreadable manifest) as a problem without re-hashing; `health` is `warning` when there are problems; `.part` files are removed at agent start and when older than 1 h, and reported once by the next scan. | Transparent status without hashing gigabytes on every poll; hashes are checked again before restore (M4). |
| D-030 | 2026-10-13 | `doctor` gains a `WARN` level (shown, does not fail the run), used for "no database chosen yet" and store problems. | A fresh controller is not broken, only unfinished. |
| D-031 | 2026-10-13 | Policy schedules are 5-field cron (`*`, `n`, `a-b`, lists, `/n` steps; day of week 0-7) plus `@hourly`, `@daily`, `@weekly`, `@monthly`, in the controller's local time, parsed by our own `scheduler` package. Day-of-month and day-of-week both restricted means either matches (classic cron). | Operators think in office hours; no dependency for ~200 lines. |
| D-032 | 2026-10-13 | A policy's destinations default to every paired node; `--to` takes a list. "Nearest node" is dropped (blueprint policy table amended). | A small office LAN has no meaningful "nearest"; one rule is easier to explain. |
| D-033 | 2026-10-13 | A policy is due when its schedule's last fire time is after the newest backup carrying its tag in that database; backups dated in the future (clock moved back) are ignored. Missed runs (agent stopped, PC off) catch up once, not once per missed slot. After a failed dump the database waits 15 min before the next try. One dump per database carries every due tag. | Survives restarts without a run log; a dead server does not produce a dump storm. |
| D-034 | 2026-10-13 | A built-in `manual` policy (no schedule, keep 10, all nodes) cannot be removed; every `backup now --tag` must name an existing policy. | A manual backup is retained like any other; a typo cannot create an unretained tag. |
| D-035 | 2026-10-13 | Retention runs per node: a node keeps the newest `keep` of each (database, tag) whose policy targets it, and drops an older copy only once that many newer ones are verified on that same node. Removing a node from a policy's destinations deletes that policy's copies there. | A node that missed backups never loses its last good copies. |
| D-036 | 2026-10-13 | Backups a node holds that this controller did not make, and backups whose tag has no policy any more, are never deleted; the first are logged once as `unknown_backup`. | Data safety beats tidiness; removing a policy never deletes data. |
| D-037 | 2026-10-13 | Reconciliation (every 5 min and when a node comes back) replaces D-026's per-status-cycle retry: a missing wanted copy is sent again while it is still staged. 507 is permanent for that attempt; a resend waits until the node reports room above its floor. | One loop owns "what should be where"; a full disk does not burn retries. |
| D-038 | 2026-10-13 | A corrupt copy (node says corrupt, or another sha256) is deleted and re-sent only when staging still has the backup; otherwise it is kept and reported. | Never trade a damaged copy for nothing; self-heal from a peer is Phase 3. |
| D-039 | 2026-10-13 | `[controller.staging] keep` is per database, 0 means 12. Staging also keeps busy dumps and anything a target node still lacks; staging files with no backup row are removed. A backup with no live copy and no staging file becomes `expired` and leaves `backups list` (see `--all`). | Bounded controller disk without losing the only copy. |
| D-040 | 2026-10-13 | The scheduler tick, `/status` poll (15 s, 3 misses = offline) and reconcile loops live in `coord` beside the transfer pool; the decision itself is the pure `retention` package. No `reconcile` package. | The loops share the controller's job and poll state; the plan is testable without I/O. |
| D-041 | 2026-10-13 | While any node is offline, reconciliation runs discovery first, so a node that changed address is found again. | DHCP leases change in small offices (D-015). |
| D-042 | 2026-10-13 | A node whose store cannot be read sends `backups: null`; the controller treats it as having no current inventory and makes no retention decision for it. | An unreadable disk must not look empty, or every copy would be re-sent and none deleted safely. |
| D-043 | 2026-10-13 | A new backup is pushed only to the union of its policies' destinations (all nodes if any policy has none, or was removed meanwhile); supersedes D-024's "every node". | A `--to`-limited policy must not fill other nodes only for retention to delete the copies. |
| D-044 | 2026-10-13 | Refines D-035: a node that no longer should hold a backup keeps its copy while a node that should hold it lacks it and staging cannot send it ("a PC that should hold it does not have it yet"). | A destination change must never delete the last copy. |
| D-045 | 2026-10-13 | An expired backup still counts toward the copies a node holds; when a node shows a verified copy again the backup leaves `expired`. | A store that read empty once (unmounted drive, moved path) must not get its returning copies deleted. |
| D-046 | 2026-10-13 | While any backup is dated after the controller's clock, retention deletes, unstages and expires nothing and says why in the plan; sends continue. | A clock set back would otherwise rank every new backup below the old ones and throw it away. |
| D-047 | 2026-10-13 | `retention run` has no 15 s client ceiling (the CLI waits up to 2 min) and a started run finishes even if the caller leaves. Only the latest failed dump per database is kept in memory and listed. The first reconcile is triggered by the first poll answer, not a 30 s timer. | Deletes are never done but left unrecorded; a weekend outage does not fill `backups list` with failures. |
| D-048 | 2026-10-13 | `sevjala setup` is an interactive install/update/uninstall wizard; a double-click on Windows (the process owns its console) runs it, relaunches through UAC when not elevated, and waits for Enter before the window closes. It copies the exe to `%ProgramFiles%\Sevjala` (`/usr/local/bin` elsewhere), runs that copy's `service install`, adds the folder to the machine PATH, then shows a pairing code (node) or asks for the database and pairs nodes (controller). Uses `golang.org/x/sys/windows` (already in the module) for UAC, PATH and the console check. No MSI/Inno installer yet. | Office operators should not need a terminal or to know where the exe must live; the wizard reuses the CLI commands, so it adds no second install path. |
| D-049 | 2026-10-13 | The local API names its own failures: a caller the pipe or socket refuses is told to use an Administrator prompt or sudo; an agent started while one already answers on the endpoint (on Windows also when the pipe exists but refuses the caller) fails with "already running". `sevjala agent` is hidden from help, since only the service runs it. `discover` and `code` say that a node on another network (Tailscale, VPN, subnet) needs `agents add <ip>` before `pair`. | Found on a real Windows 11 PC: a non-admin prompt, a mistyped `agent`, and pairing over Tailscale all ended in a bare "Access is denied" or a dead end. |
| D-050 | 2026-10-13 | Builds between releases are versioned `<last tag>+<commits since it>`, with `.dirty` for uncommitted changes (e.g. `0.3.0-alpha.1+4`). The Makefile computes it for `build`, `build-all` and `build-win7`; real releases keep the tag. | Test PCs showed the same `0.3.0-dev` for different builds, so nobody could tell which one was installed. |
| D-051 | 2026-10-13 | Errors an operator sees say what is wrong and what to do, never a pipe path, URL, HTTP method, exe path, `exit status`, errno or certificate hash. Each kind is translated once where it is made: local service calls (`cmd` `agentProblem`: not installed / stopped / starting / not admin / busy / restarted), LAN calls (`lanapi` `send`: refused / timeout / unreachable or isolated / unknown name / not a Sevjala agent / identity changed / connection dropped), MySQL (`dump` `explain`: not running / wrong password / unknown database / no rights / disk full) and the keyring. The original error stays wrapped for code and the log. `service start`/`stop` succeed when already running/stopped; `doctor` needs admin and gives each query its own timeout. | Operators on a real PC got raw Go and OS error chains they could not act on. |
| D-052 | 2026-10-13 | `sevjala agents remove <agent> [--force]` forgets a node on the controller only: its row, its copy records and its place in policy destinations. Files on the node stay; nothing is sent to it. Refused while a policy sends only to that node (an empty list would mean every node), and without `--force` while a live backup's only verified copy is there. | Blueprint CLI lists `agents remove`; removal must never delete backups or silently widen a policy. |
| D-053 | 2026-10-13 | Discovery stays LAN broadcast on every local adapter; it does not probe VPN or Tailscale peers. Nodes on another network are added by address (`agents add <ip>`). | Tailscale has no broadcast; probing a tailnet would depend on its CLI, touch unrelated devices and break the LAN-only scope (AD-17). |
| D-054 | 2026-10-14 | `sevjala backups export <backup\|latest\|all> [--db NAME] [--to FOLDER] [--force]` copies a backup this PC holds (a node's store or the controller's staging) through the local API into `<FOLDER>/<database>/<yyyy-mm-dd_hh-mm-ss>.sql.gz` plus `.json`, written by the calling user. It is checked against the manifest's size and sha256 through a temp file and rename; an existing file needs `--force`; Sevjala's copy is untouched. `all` copies every held backup and skips those already in the folder, so repeating it copies only new ones. On a node `backups list` lists what it holds. Store and staging keep their `BK-…` names. | Operators could not open their own backups: the store is root/SYSTEM-only (D-010). A copy outside it keeps the store locked while the operator gets a file they own, sorted by database and time. |
| D-055 | 2026-10-14 | AD-18 accepted by the owner. `sevjala update [--from FILE]` (admin) picks the newest non-draft GitHub release by semver, pre-releases only when the PC already runs one; Windows takes `sevjala-win7-<arch>.exe` (runs on 7 to 11). It downloads into the install folder, checks the sha256 from `checksums.txt`, runs `<file> version` to confirm it starts and is that version, then does setup's update: stop, replace (the previous binary is kept as `sevjala.old`/`sevjala.exe.old`, since Windows can rename but not overwrite a running exe), start; a failed start puts the previous binary back and starts it. A build equal to the release (e.g. `0.3.0-alpha.1+16` vs `0.3.0-alpha.1`) counts as up to date. Nodes are not updated over the LAN. | Copying a new exe to each PC by hand was the main update chore; checksum, run check and rollback keep a bad download from leaving a PC without backups. |
| D-056 | 2026-10-16 | `sevjala restore --file PATH` restores a `.sql.gz` exported by `backups export`, checked against the `.json` beside it (size and sha256) before anything is loaded; a mismatch marks nothing in the catalog. The CLI makes the path absolute; the agent refuses a relative path, a non-regular file or a missing manifest (400). | When the controller PC dies, a new controller cannot fetch from the old one's nodes (a node accepts one controller): export on a backup PC, copy the file over, restore it. |
| D-057 | 2026-10-16 | A restore goes into a new database by default, `<db>_restored_<yyyymmdd_hhmm>` (the backup's local creation time, `db` trimmed to fit 64), created with the source database's character set and collation when it still exists. An existing target is refused (409); names are 1-64 of `[A-Za-z0-9_$-]` so they are quoted without escaping. `latest` is the newest backup of `--db` (or the only configured database) that has the controller's own copy or a verified copy. | Production is never touched without `--replace-production`; a fixed pattern makes restored copies easy to find and drop. |
| D-058 | 2026-10-16 | The pre-restore backup of `--replace-production` is an ordinary `BK-` backup tagged `manual`, not the blueprint's `PRE-RESTORE-<ts>` file. The restore waits until it is in the catalog; if it fails, production is untouched. | A non-`BK-` staging file would be pruned as an orphan and never reach a node; an ordinary backup is distributed, listed, kept by `manual`'s keep count and restorable with the same command. |
| D-059 | 2026-10-16 | Restore sources, in order: the controller's own copy, then every answering node (`online` or `warning`) with a verified copy, newest `verified_at` first; each failure is logged (`restore_source_failed`) and the next is tried. A node copy is downloaded to `staging/<id>.restore.part` while hashing and deleted afterwards. A node copy with the wrong size or sha256 (including the node's 422 for a file shorter than its manifest) is marked `corrupt`; a damaged own copy is deleted and unstaged. | A `warning` node (low disk, one bad file) still holds good copies; a damaged copy must never be loaded, and marking it lets retention replace it. |
| D-060 | 2026-10-16 | One restore at a time (409 naming the running one); it runs on the agent's lifetime, so closing the CLI does not stop it, and the backup it reads counts as busy for retention. `--replace-production` is refused while that database is dumping, and from after the pre-restore backup until the load ends every backup of it is refused (409, the scheduler logs `schedule: backup not started` and fires on its next due tick). | No backup may capture a half-loaded database, and two restores would compete for the same MySQL. |
| D-061 | 2026-10-16 | A failed load into a new database drops that database and says so. A failed `--replace-production` after the drop leaves production partly loaded and the error names the way back: `sevjala restore <pre-restore id> --replace-production`. The node's `GET /backups/{id}` answers 503 while the backup is received or deleted (the spec said 409; 503 matches `PUT` and `DELETE`) and 422 for a damaged file. | MySQL cannot swap databases atomically (blueprint: drop and reload); the operator gets a single command instead of a recovery procedure. |
| D-062 | 2026-10-16 | `POST /restore` takes `dry_run`: it resolves and checks the request (backup, target, existence) without starting, so the `--replace-production` confirmation shows the backup, its date and size before the operator types the name; the agent itself also requires `confirm` equal to the database. `sevjala restore --status` follows the running or last restore. On a node, `restore` answers how to export the file and restore it on the controller. | The CLI must not duplicate the controller's choice of backup; Ctrl-C must not leave the operator without a way to watch again. |
| D-063 | 2026-10-16 | After the final review: (1) every restore holds backups of its target from create to the end, not only a replace, so `--into <configured name>` cannot be dumped half loaded; (2) a replace that fails after the drop (load error or service stop) leaves `<data-dir>/replace-incomplete-<db>` naming the pre-restore backup; while it exists backups of that database are refused with the way back, and the next replace skips its own pre-restore backup (the database is already broken) and removes the file when it succeeds. Deleting the file by hand is the escape hatch; (3) `latest` only counts copies on answering nodes; (4) restore names may not start with `-` (the mysql client would read one as an option); (5) `--file` is copied into `staging/<id>.restore.part` while it is checked and the copy is loaded, so the file cannot change between check and load; (6) the CLI sends the backup id it showed, not `latest`, after the typed confirmation; (7) service stop waits up to 20 s for a restore to drop its half-made database and log; a node fetch has the stall bound from the first byte of the dial. | Review found each of these could load or back up the wrong data, or leave the operator without a record. |
| D-064 | 2026-10-17 | Owner decisions after M4: (1) AD-19 accepted, restore checks a file before loading it, so it reads it twice; (2) changed the same day by the owner: the pre-restore backup of `--replace-production` is tagged `pre-restore` (not `manual`, amending D-058), a built-in policy with no schedule and keep 5 per database that cannot be removed (store migration 4 adds it with `INSERT OR IGNORE`, so a policy of that name made by hand is kept). `policy list` shows it as "before a restore replaces the database"; `policy set pre-restore --keep N` changes the count. | Many replaces in a row would otherwise push the operator's own manual backups out of `manual`'s keep count. |
| D-065 | 2026-10-17 | A copy the controller read and found damaged (a restore's sha256 check) stays `corrupt` with `last_error` "damaged: its sha256 did not match when the controller read it", even when the node's inventory (size + manifest only) still lists it as verified; retention deletes it on the node and sends the controller's good copy again, or keeps it marked damaged when the controller has none. Found on the M4 node smoke: the copy went back to verified 5 min after the restore refused it. |
| D-066 | 2026-10-17 | AD-20 accepted by the owner (amends AD-13): daily commands need no administrator; the agent checks the caller per request and refuses admin-only actions with 403 `admin_required`; the CLI re-runs the command elevated (UAC on Windows, `sudo` on macOS/Linux, "Cancelled: administrator rights were refused; nothing was changed." when refused).
